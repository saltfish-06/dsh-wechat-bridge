# 架构

## 为什么要拆成两半

微信 PC 端的自动化有两个硬性前提：

1. **要读本地数据库**（消息内容走 SQLCipher 加密，密钥在微信进程内存里）
2. **要模拟鼠标键盘**（发消息靠 UIA 控件树 + 坐标点击）

第 2 条决定了：**自动化必须有一个人在旁边看着的、解锁的桌面**。
在你自己正在用的主机上跑，机器人每次发消息都会抢走焦点和鼠标。

所以拆成：

- **虚拟机**：只负责"操作微信"这一件事。它的鼠标被抢无所谓，它本来就没有人用。
- **主机**：负责 Agent、人设、白名单、会话状态。这些是你的东西，不该进虚拟机。

两边用一个极简的 HTTP 接口对话，中间靠 VirtualBox 的 NAT 端口转发打通。

## 数据流

### 收消息

```
微信写入本地 SQLite
      ↓  （适配器每 0.8 秒轮询一次增量）
adapter.py 解析出 chat / sender / content
      ↓  过滤：自己发的（回声）、XML 系统消息、非白名单
放进内存队列 _queue
      ↓  （主机每 0.5 秒拉一次 GET /recv）
bridge.py 去重（chat + 时间戳 + 内容前 60 字）
      ↓  白名单校验；是「/人设」指令就地处理
丢进工作队列 → 单个 worker 线程串行处理
```

**为什么串行**：并行问 Agent 会让同一个微信会话的历史乱序，而且虚拟机那边的
UIA 发送本来就不能并发（它要独占鼠标）。

### 回消息

```
bridge.py 拿到 Agent 的回复文本
      ↓  按空行切段（最多 3 段），一段一条微信消息
POST /send  {chat, text}
      ↓
adapter.py 先把自己的发送记进 _sent（**必须在真正发出去之前记**）
      ↓
WeChatGUI.send_msg()  →  UIA 找窗口 → 点搜索 → 输入 → 回车
```

**"先记账再发"这个顺序不能改**：消息落库比 `send_msg()` 返回要早，
监听线程会先捞到它。记晚了，机器人就会回复自己。

## 接口

适配器只暴露三个端点。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/status` | `{"ok":true,"ready":bool,"account":"...","wxid":"...","queue":N}` |
| GET | `/recv` | 取走并清空来信队列：`{"messages":[{chat,name,content,ts}, ...]}` |
| POST | `/send` | 体 `{"chat":"wxid_xxx","text":"..."}` |

`ready` 是"微信登录好了没"。**没登录时 `/send` 会先等 30 秒**（你可能正在扫码），
等不到才返回错误。

鉴权：如果 `adapter-token.txt` 存在，所有请求都要带 `X-Adapter-Token` 头。
不配就完全放行——**只应通过绑在 `127.0.0.1` 的端口转发访问**。

## 关键设计决定

### 人设放在主机，用 patch 注入

Agent 每次被调用都是新进程，人设通过 `--patch` 传进去：

```
persona/<代号>.md  ──build_persona.py──▶  personas/<代号>.yml
                                              ↓
                                    dsh --patch <这个文件> -
```

**切换人设不需要重启任何东西**，因为 patch 是每次调用现挑的。
`persona.txt` 里存当前代号，改完下一条消息就生效。

### 会话连续性

`state.json` 里存 `{"<chat>": {"session_id": "..."}}`。
同一聊天的历史由 Agent 自己维护，桥接只负责把 session id 传回去。

会话文件被别的进程锁住时（Agent 上次超时留下的僵尸进程），桥接会
**丢掉 session id 重试一次**——代价是那段历史断了，但机器人不会哑掉。
只重试一次，因为不带 session id 还报同样的错就说明问题不在会话上。

### 登录看门狗

微信重启后停在登录页时，**不能去碰 UIA**——实测 `ensure_window()` 不会返回
False，而是无限期挂住（卡了 4 分钟没动静）。

所以用窗口宽度判断：登录页 274×380，主窗口 ≥500。纯 `pygetwindow`，秒回。

适配器启动时如果发现没登录，**转入等待模式**：HTTP 接口照开，后台每 20 秒
重试一次。你什么时候扫码都行，扫完 20 秒内它自己就活了。

## 资源占用

| 项 | 值 |
|---|---|
| 虚拟机内存 | 配置 6 GB，实际工作集约 6.3 GB |
| 虚拟机 CPU | 4 核 |
| 端到端延迟 | 约 7~10 秒（轮询 1.3s + Agent 3~4s + 发送 3s） |
| 首次发送 | 慢（要初始化 GUI 与校准），所以适配器启动时预热 |

**VirtualBox 的内存气球对 Windows 客体无效**（实测命令返回成功但占用一点没变），
所以想省内存只能改配置 + 重启虚拟机。
